# Specview

**Specview** is a small, read-only dashboard for observing Markdown specifications as they move through an agentic software-development workflow.

Website: **specview.sh**

> The domain is the canonical product home. During the proof of concept, binaries are distributed through GitHub Releases.

See [`SPEC.md`](SPEC.md) for the canonical v0.0.1 POC specification.

## Architecture

Specview observes a project filesystem. The filesystem is the source of truth for repo-native intent. Specview does not edit specifications or manage their state.

The longer-term architecture separates three dimensions:

```text
INTENT | EXECUTION | EVIDENCE
```

Repository specification adapters normalize Intent. Runtime/SCM adapters will normalize Execution. Evidence adapters normalize verification results without making Specview the test runner or CI system.

```text
agent / developer
      -> edits repo-native specifications
      -> Specview observes
      -> live dashboard updates
```

Specview-owned runtime material uses the ignored `.specview/` directory. Durable configuration remains in `.specview.yaml`.

## Try the ephemeral demo

The canonical demo is an agent-executable recipe, not a persistent project.

Recipe:

```text
https://raw.githubusercontent.com/sergii/specview/feat/ephemeral-demo/demo.md
```

Give any coding agent a short instruction such as:

```text
Read the Specview demo recipe at the URL below and execute Phase 1 exactly:
https://raw.githubusercontent.com/sergii/specview/feat/ephemeral-demo/demo.md
```

The agent creates an isolated OS temporary directory using the semantic form:

```text
specview-demo-<opaque-session-id>
```

The opaque session identifier is generated by the operating system and must not contain username, hostname, device name, repository name, Git SHA, or other personal information.

The demo lifecycle is:

```text
prepare
  -> agent creates temporary .specview.yaml + specs/
  -> agent prints the temporary path and waits

observe
  -> user starts Specview in that directory

run demo
  -> agent performs visible status transitions with pauses

cleanup
  -> only after explicit user instruction, agent removes the temporary directory
```

The demo is repeatable, disposable, and safe to run concurrently in multiple agent sessions. Specview itself has no demo-specific code path and ships no demo dataset.

The repository `sergii/specview-demo` may remain as a temporary development/integration fixture, but it is not required for the public demo flow.

## Dogfooding

Specview itself is also a Specview project. This repository contains `.specview.yaml` and real specifications under `specs/`.

```bash
git clone https://github.com/sergii/specview.git
cd specview
specview
```

The source repository is therefore the real-world dogfooding example, while `demo.md` provides a deterministic synthetic demonstration.

## Install

After the first GitHub Release is published:

```bash
curl -fsSL https://raw.githubusercontent.com/sergii/specview/main/install.sh | sh
```

The installer detects macOS/Linux and amd64/arm64, downloads the matching release archive, verifies its SHA-256 checksum, and installs `specview` to `~/.local/bin` by default.

The future canonical installer will be:

```bash
curl -fsSL https://specview.sh/install | sh
```

## Initialize a project

```bash
cd your-project
specview init
```

This creates native Specview configuration and an artifact root when no stronger supported SDD convention is detected.

Typical native layout:

```text
.specview.yaml
specs/
```

Default native configuration:

```yaml
version: 1

project:
  name: ""
  root: "."

specs:
  adapter: specview
  path: specs
  pattern: "*.md"

server:
  host: 127.0.0.1
  port: 7331
```

`project.name` is optional. When empty, Specview uses the observed project directory name.

`project.root` defaults to `.`. Relative roots are resolved from the directory containing `.specview.yaml`; `specs.path` is then resolved from the observed project root.

The leading dot in `.specview.yaml` is intentional: it is tooling metadata, not project documentation.

## Specification status contract

Native Specview specifications are regular Markdown files. Status is namespaced under `specview` in YAML front matter:

```markdown
---
specview:
  status: in_progress
---

# Transactional Outbox

Implementation notes go here.
```

The POC has exactly three valid statuses:

```text
new
in_progress
done
```

A specification without front matter defaults to `new`. An unknown status remains visible in the dashboard under **Metadata errors** instead of being silently ignored.

## Evidence contract

The normalized Evidence layer is documented in:

```text
specs/H11-normalized-evidence-contract.md
docs/evidence/native-evidence.md
```

The first passive bridge observes strict JSON evidence records under:

```text
.specview/evidence/
```

Evidence is revision-scoped and distinguishes a stable logical `check` from the concrete `provider` that produced it. Acceptance policy is intentionally a separate follow-up layer.

## Observe

Start Specview from a configured project directory:

```bash
specview
```

or:

```bash
specview serve
```

The server binds to the configured local address and renders the current read-only dashboard.
